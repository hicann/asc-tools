# npu-check 算子正确性检查

使用本 Skill 回答四个问题：当前算子是否适合运行 `npu-check`、应检查什么、报告说明了什么，以及报告如何指导
算子修改和复测。

## 何时使用

运行前先读取[适用范围与限制](references/applicability.md)。仅在全部运行条件满足时使用 `npu-check`；否则说明
不支持的具体条件。

| 算子开发场景 | 检查目标 | 检查类型 |
| --- | --- | --- |
| 新算子已能运行，需要补充 Device 侧正确性检查 | 检查已执行路径中的受支持 GM 访问和同步配对 | 按风险选择，必要时同时启用 |
| 修改 Tiling、GM offset、搬运长度、stride、block 划分或尾块处理 | 检查数据搬运是否读写越界 | `memcheck` |
| 出现 AICore Error、结果偶发异常，怀疑地址或搬运参数错误 | 定位访问方向、大小、源码位置和执行上下文 | `memcheck` |
| 修改流水同步、flag/event ID、buffer 获取释放或条件分支 | 检查同步操作是否精确配对 | `synccheck` |
| 算子卡住或长期等待，日志停在同步附近 | 查找重复执行、缺少配对操作或两侧执行次数不一致 | `synccheck`，并对同步调用设置超时 |
| 同时修改数据搬运和同步逻辑 | 分别检查两类风险 | `memcheck` 和 `synccheck` |

## 可以检查什么

- `memcheck` 检查本次运行中受支持搬运指令的 GM 读写，提供访问方向、访问大小、源码位置、
  core/block/pipe/launch 和异常地址，可用于定位越界访问及已释放内存访问。
- `synccheck` 检查 `SET_FLAG -> WAIT_FLAG` 和 `GET_BUF -> RLS_BUF` 是否精确配对，报告触发操作、相关或
  期望操作、源码位置、launch 和 pair key，可区分前置操作重复执行、配对操作缺失和两侧执行次数不一致。

同步指令存在硬件配对限制：`SET_FLAG/WAIT_FLAG`、`GET_BUF/RLS_BUF` 必须在每条实际执行路径上按相同
pair key、相同次数成对使用。分支、循环、尾块和提前返回都不能留下只执行一端的路径。

检查能力及结论边界统一以[适用范围与限制](references/applicability.md)为准。

选择前读取[场景与检查类型选择](references/tool-selection.md)。检查类型应根据待检查的风险选择，不能仅根据
AscendC 或 C Device API 名称推断完整覆盖。当前工具帮助和官方文档未明确说明的覆盖范围应标记为未知。

## 工作流程

1. **确定验证场景。** 记录算子变更、可疑现象、目标 shape、正常/边界/尾块输入，以及能够复现该路径的最小
   可执行应用。先按[适用范围与限制](references/applicability.md)完成检查。
2. **选择检查能力。** 根据[场景与检查类型选择](references/tool-selection.md)选用 `memcheck`、`synccheck`
   或两者。遇到具体 API 是否支持的问题时，以当前 `npu-check --help`、CANN 官方文档和实际报告为依据；证据
   不足时说明覆盖未知，不追踪工具内部源码补充结论。
3. **受控运行。** 检查 `command -v npu-check` 和 `npu-check --help`，保留应用原有工作目录、参数、环境和
   Device 选择，按照[运行 npu-check](references/execution.md)保存未经改写的原始 stdout/stderr、执行命令和
   进程退出状态。疑似卡死且可以修改
   测试应用时，可将 `aclrtSynchronizeStream` 临时替换为 10 秒有界同步；超时后配合
   `aclrtDestroyStreamForce` 强制销毁阻塞的 stream，使测试程序进入失败退出流程，外层仍使用已有测试预算兜底。
4. **判断报告可靠性。** AI 直接阅读原始报告以及对应的命令、环境、检查类型和退出状态，结合信息来源、上下文
   连续性、诊断与汇总是否自洽、是否存在截断或消息丢失迹象，以及现有信息能否支撑结论，判断报告为“可靠”、
   “部分可靠”或“不可靠”并解释理由。不得通过固定文案、正则字段或字段是否存在机械核对报告。部分可靠的报告
   可以保留上下文足以支撑的明确诊断，但不能扩展为完整通过结论。具体方法见
   [报告阅读](references/result-interpretation.md)。
5. **把诊断映射到算子代码。** 根据源码位置、Device Frames、访问大小、block/pipe/launch 或同步 pair key，
   读取[从报告改进算子](references/operator-improvement.md)，形成由报告证据支持的修改假设。不要只根据错误类型
   给出泛化建议。
6. **修改与复测。** 仅在用户授权修复时修改算子。先用相同命令、shape 和检查类型验证原问题消失，再补跑
   正常、边界和尾块 shape；数值精度测试仍需独立通过。没有获得修改授权时，只报告定位结果和建议。
7. **处理受限结果。** 报告不完整、自相矛盾、来源不明或命令无法启动时，读取
   [故障排查](references/troubleshooting.md)。说明哪些信息仍可作为证据、哪些结论无法确认；只有改变了明确的
   失败条件后才重试。

## 报告输出

面向用户的结果按以下顺序组织：

1. **场景与范围**：算子、输入 shape、应用命令、工作目录、检查类型和当前已知覆盖边界。
2. **报告可靠性**：可靠、部分可靠或不可靠，以及支持该判断的来源、连续性、自洽性和缺失信息。
3. **检查结论与关键证据**：明确发现的问题或当前无法确认的结论、应用自身状态、首个相关诊断、源码位置、
   访问或同步上下文和原始日志路径。
4. **算子修改建议**：每条建议都说明它依据哪个报告字段，优先检查哪段 Tiling、搬运或同步代码。
5. **复测状态**：是否用同一输入复测，是否扩展边界 shape，精度测试是否独立完成。

```text
检查场景：<算子变更、症状和输入 shape>
检查范围：<应用命令、检查类型、已验证能力和未覆盖边界>
报告可靠性：<可靠/部分可靠/不可靠及判断理由>
检查结论：<明确问题、未发现明确问题或无法确认，以及应用状态>
关键证据：<原始报告中的诊断、源码位置、访问/同步上下文和日志路径>
修改建议：<报告字段 -> 根因假设 -> 具体检查或修改点>
复测：<同条件复测、扩展 shape 和独立精度结果>
```

“未发现明确问题”的表述按[适用范围与限制](references/applicability.md)收敛。只有可靠报告才能支撑本次执行
范围内的通过结论；未实际执行时，不得声称完成了真实 NPU 验证。

## 信息来源

命令参数以当前环境的 `npu-check --help` 为准；检查能力和报告字段以当前版本的 CANN 官方文档及实际输出为准。
不同版本存在差异时，记录工具版本和实际输出；官方资料与本次报告未提供的信息一律标记为未知，不通过分析
`npu-check`、Devkit 或编译器内部源码补充用户使用结论，也不得补造参数、字段或检查能力。

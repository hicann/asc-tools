# 报告阅读

AI 直接阅读未经改写的原始报告和运行上下文，先判断报告可靠性，再提取检查结论和诊断证据。不要通过固定文案、
正则字段、字段是否存在或字段排列顺序机械核对报告；不同 CANN 版本的表达可以不同，判断必须说明语义依据。

## 第一层：确认信息来源

将以下信息与原始报告一起阅读：

- 产生报告的完整命令、工作目录和进程退出状态；
- 目标 NPU、CANN 安装来源、`npu-check` 路径和版本；
- 本次启用的检查类型、输入 shape、Device 选择和外层测试预算；
- 原始 stdout/stderr，以及使用 `--log-file` 时分别保存的工具报告和终端输出。

报告来自未知来源、经过手工拼接、跨版本混用，或无法与某次执行建立对应关系时，不能把它作为可靠验收证据。

## 第二层：由 AI 判断可靠性

AI 综合判断以下语义，而不是逐字匹配某一行：

1. 日志是否保留了足够的起止上下文，能否看出工具实际启动、执行和结束情况。
2. 检查类型、具体诊断、汇总信息、应用行为和退出状态是否相互支持，是否存在无法解释的冲突。
3. 是否有超时、信号终止、明显截断、消息丢失、工具初始化失败或日志片段缺失的迹象。
4. 诊断是否包含支撑定位所需的上下文，例如检查类型、错误位置、访问参数或同步 pair key。
5. 当前证据能支持“发现明确问题”“本次受支持范围内未发现问题”，还是只能说明执行失败或信息不足。

使用以下等级，并写出具体理由：

| 可靠性 | 使用方式 |
| --- | --- |
| 可靠 | 来源和运行上下文清楚，关键信息连续且自洽，足以支撑本次检查结论。 |
| 部分可靠 | 报告被截断或存在缺失，但某些明确诊断有充分上下文支撑；保留这些诊断，同时限制结论。 |
| 不可靠 | 来源不明、关键上下文缺失、明显拼接、环境不匹配或关键信息冲突，无法据此确认检查结论。 |

“部分可靠”不是“全部无效”。例如超时前完整输出的 GM 越界诊断包含访问方向、大小、源码位置和异常地址时，
可以作为本次路径存在问题的证据；但不能据此断言分析已经结束、错误总数已结算或其他检查类型没有问题。

## 第三层：区分检查结论和应用状态

应用失败与检查类型发现问题是两个维度，应分别说明：

- 报告中存在上下文充分的明确检查诊断时，直接报告该问题，并单独说明报告可靠性和应用状态。
- 可靠报告在本次已启用检查类型的受支持范围内未发现问题时，只能给出受限的本次通过结论。
- 部分可靠报告没有明确诊断时，不能因为暂时没有看到错误而声明通过。
- 不可靠报告不能支撑检查结论；其中可确认的环境错误或命令错误仍可作为故障排查证据。

不要仅凭进程退出码、单条汇总或某个固定字段下结论。发现信息冲突时，明确列出冲突并降低可靠性判断。

## 第四层：读取 Memcheck 诊断

| 报告信息 | 含义 | 对算子定位的作用 |
| --- | --- | --- |
| `Invalid GM read/write of size N bytes` | 访问方向和本次访问字节数 | 判断是输入读取还是输出写回，并核对元素数到字节数的换算 |
| `location` | 符号化后的函数、文件和行号；失败时可能只有 PC/kernel | 优先定位 Device Frames 中最接近用户算子代码的调用点 |
| `aicore/type/block/pipe/launch` | 发生问题的执行实体和下发批次 | 判断问题是否只发生在某类 core、某个 block、某条搬运流水或某次 launch |
| `Address ... is out of bounds` | 访问区间不属于当前有效范围 | 检查 GM offset、搬运长度、stride、Tiling 边界和尾块保护 |
| `used after free` 及 allocation 信息 | 地址属于已经释放的分配 | 检查 Host/Device 异步执行期间的 buffer 生命周期和同步时机 |
| `Device Frames` | 报告提供的 Device 调用栈 | 沿栈找到算子内实际发起搬运的位置，不把系统库位置直接当作根因 |

例如，报告同时给出 `Invalid GM read of size 32 bytes`、`MTE2`、`launch (1)` 和算子源码行时，可得出的
直接事实是：该次 launch 的对应搬运路径在该源码点发生了 32 字节 GM 越界读。至于根因是尾块、offset、长度
还是 stride，需要回到该行参数和 Tiling 数据验证，不能由错误标题直接断定。

源码行号依赖算子编译时保留行号信息。报告只有 kernel 名称和 PC 时，先用这些信息缩小范围，再按项目已有构建
方式重新编译并复测；不要编造源码位置或未经当前项目验证的编译参数。

## 第五层：读取 Synccheck 诊断

同步指令的硬件限制是：`SET_FLAG/WAIT_FLAG`、`GET_BUF/RLS_BUF` 必须在每条实际执行路径上按相同 pair key、
相同次数成对使用。任何分支、循环、尾块或提前返回路径都不能只执行一端；当前 shape 没有卡死也不能证明单边
调用合法。

| 报告信息 | 含义 | 对算子定位的作用 |
| --- | --- | --- |
| mismatch reason | 前置操作重复执行、配对操作缺失或两侧次数不一致 | 确定缺少的是 SET/WAIT 或 GET/RLS 的哪一端，或哪一端被重复执行 |
| trigger point | 实际触发诊断的操作及源码位置 | 定位当前 `SET/WAIT` 或 `GET/RLS` 调用 |
| related/expected point | 已存在的相关操作，或本应出现的操作 | 对照同步对的另一侧及其代码路径 |
| pair kind/key | 配对协议以及 src/dst pipe、event/buffer 标识 | 核对两侧是否使用完全相同的同步 key |
| launch ID | 当前诊断所属的 kernel 下发 | 标识当前受支持的单次调用，不能据此推断多次调用也受支持 |

若错误只在特定 shape 出现，应重点比较该 shape 下的条件分支、循环次数和提前返回路径。具体修改方法见
[从报告改进算子](operator-improvement.md)。

## 通过结论的边界

只有判断为可靠的报告才能支撑“本次受支持范围内未发现问题”。完整边界见
[适用范围与限制](applicability.md)。回答应明确写出本次输入、应用命令、检查类型、报告可靠性和覆盖边界，并将
精度与性能验证作为独立证据。

# 从报告改进算子

报告提供的是运行时证据，不是自动修复结论。先定位报告中的事实，再形成可验证的根因假设，最后进行最小修改和
同条件复测。

## 通用定位步骤

1. 从首个相关诊断开始，记录检查类型、错误类型、launch、block/core、pipe 和源码位置。
2. 沿 Device Frames 找到最接近用户算子源码的调用点，不把系统库或公共 API 位置直接当作根因。
3. 对 memcheck 重建“有效分配范围、起始 offset、访问元素数、元素字节数和 stride”；对 synccheck 核对一组
   `SET_FLAG/WAIT_FLAG` 或 `GET_BUF/RLS_BUF` 是否在同一 launch 中成对执行，并检查两端的 src/dst pipe、
   event ID 或 buffer ID，以及分支、循环和提前返回是否导致一侧少执行或多执行。
4. 提出一个能解释报告全部关键字段的根因假设，并指出需要查看的具体变量或代码分支。
5. 做最小修改后，先用产生原报告的同一命令、shape 和检查类型复测。
6. 原问题消失后，再覆盖正常、边界、尾块和相邻 shape，并独立运行数值精度测试。

## Memcheck 报告到修改点

| 报告证据 | 优先检查 | 常见修改方向 |
| --- | --- | --- |
| GM `read` 越界 | 输入 GM offset、每个 block 的起点、实际输入长度、尾块有效元素数 | 修正 Tiling 边界；限制最后一次搬运长度；避免用对齐后长度读取真实分配范围之外的数据 |
| GM `write` 越界 | 输出 GM offset、输出分配大小、写回长度、尾块有效元素数 | 修正输出 offset 或写回长度；仅写回有效元素；保证 Host 分配与 kernel 契约一致 |
| `size N bytes` 与预期不符 | 元素个数、数据类型字节数、API 参数单位、burst/block 长度 | 修正元素数与字节数换算；核对长度和 stride 的单位，不用经验值替代接口契约 |
| 只在特定 block/core 出错 | block 起始 offset、blockDim、均分与余数、尾块分支 | 将余数分配和 block 边界写入 Tiling；确保无数据 block 不进入搬运路径 |
| `used after free` | Host 释放顺序、异步 kernel/stream 完成时机、buffer 复用 | 延长 buffer 生命周期；在确认 Device 使用结束后再释放或复用；核对 stream 同步关系 |

修改前要用实际分配范围验证假设。例如报告给出“地址越界”和“访问 32 字节”，只能证明该访问区间非法；如果
没有分配边界信息，还需要从 Host 分配、kernel 参数和 Tiling 中还原合法范围，不能直接猜测应减少多少元素。

## Synccheck 报告到修改点

硬件要求 `SET_FLAG/WAIT_FLAG`、`GET_BUF/RLS_BUF` 在每条实际执行路径上按相同 pair key、相同次数成对使用。
检查分支、循环、尾块和提前返回时，应分别验证动态执行次数，不能用另一条路径上的操作补足当前路径，也不能以
当前 shape 未复现卡死为由保留单边同步指令。

| 报告原因 | 优先检查 | 常见修改方向 |
| --- | --- | --- |
| `duplicate_opens` | 同一 key 的 `SET_FLAG`/`GET_BUF` 是否在循环或分支中重复执行 | 删除重复执行，或确保前一次操作先由对应的 `WAIT_FLAG`/`RLS_BUF` 完成配对 |
| `unmatched_closes` | 对应的 `SET_FLAG`/`GET_BUF` 是否未执行；两端的 key 是否不同 | 补齐前置操作；统一 src/dst pipe、event ID 或 buffer ID；修正只执行 `WAIT_FLAG`/`RLS_BUF` 的分支 |
| `unconsumed_opens` | 退出、循环结束或同步结算前是否遗漏 `WAIT_FLAG`/`RLS_BUF` | 补齐等待或释放；让两端经过相同条件；处理提前返回和尾块分支 |
| 同一源码在部分 shape 出错 | shape 是否改变循环次数、核数、分支或流水选择 | 保证各实际执行路径上的同步次数一致，不只修正常规 shape |

pair key 是配对证据。操作名称相同但 src/dst pipe、event ID 或 buffer 标识不同，仍可能无法匹配；反之，不应
为了消除报告而随意统一 key，必须先确认数据依赖和流水语义确实要求两者配对。不需要同步时应同时移除配对双方，
不能只删除或只保留其中一端。

## 修改与复测记录

每次修改至少记录：

- 原始报告中的错误类型、源码位置和关键上下文；
- 根因假设以及它对应的 Tiling、搬运参数、生命周期或同步代码；
- 实际修改内容；
- 同一复现命令的复测结论；
- 新增的边界/尾块 shape 及独立精度结果；
- 仍未覆盖的检查类型、输入、执行路径或运行环境限制。

若修改后错误位置或类型发生变化，应把它视为新的证据重新分析，不能仅因为原错误消失就宣告问题全部修复。

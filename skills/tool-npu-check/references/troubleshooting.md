# 故障排查

报告被判断为部分可靠或不可靠，或者命令无法启动时，使用本参考。先保留未经改写的原始日志和运行上下文，再处理
能够明确确认的失败条件。

## 环境未加载或命令不可用

优先复用应用正常运行时使用的 CANN 环境加载脚本。项目没有自带入口时，加载目标安装包的环境脚本，再核对
命令和版本目录：

```bash
source <CANN-install-dir>/cann/set_env.sh
command -v npu-check
printf '%s\n' "${ASCEND_HOME_PATH}" "${ASCEND_TOOLKIT_HOME}"
npu-check --help
```

当前 CANN 包的环境脚本会把安装目录的 `bin` 和 `lib64` 加入搜索路径，并设置 `ASCEND_HOME_PATH`、
`ASCEND_TOOLKIT_HOME`。如果找不到命令，或命令路径不属于目标安装目录，应先修正环境来源，不要从另一套 CANN
安装中单独拼接可执行文件或动态库路径。

还要确认应用符合[适用范围与限制](applicability.md)。不满足时不运行工具，不能通过混用其他安装包补齐命令。

## 共享库加载失败

未加载当前 CANN 环境时，工具可能在启动前报告 `libunified_dlog.so` 等共享库无法打开。遇到这类错误：

1. 重新加载与目标应用相同安装包的 `cann/set_env.sh`；
2. 再次执行 `command -v npu-check` 和 `npu-check --help`；
3. 若仍失败，记录缺失库名称、命令路径、两个 CANN 环境变量和完整错误。

不要通过手工追加其他安装目录到 `LD_LIBRARY_PATH` 来绕过错误。命令与依赖来自不同 CANN 包时，即使能够启动，
检查结果也不具备可信的版本边界。

## 参数或应用入口错误

当前公开命令行只包含 `--tool`、`--log-file`、`-h/--help` 和 `--`：

- `--tool` 只接受 `memcheck` 或 `synccheck`，可重复指定；未指定时默认使用 `memcheck`；
- `--log-file` 的父目录必须已经存在，目标必须是文件路径，同名文件会被覆盖；
- 当应用路径或参数以 `-` 开头时，必须使用 `--` 分隔；
- 被检查对象必须是能够脱离 `npu-check` 独立启动的可执行应用。

应用形态不符合[适用范围与限制](applicability.md)时，应停止运行并说明不支持，不能根据一次结果外推。未知检查
类型、缺少参数或缺少应用都说明命令没有完成预期检查；这类原始错误可用于修正命令，但不能支撑算子检查结论。

## 工具启动或基础设施失败

工具初始化报错、依赖加载失败或设备不可用表示检查流程没有按预期运行。不要依赖某一条固定状态文字判断，而应
结合命令、环境、工具实际输出和进程退出状态确认失败发生在哪个阶段。按顺序确认：

1. 应用脱离 `npu-check` 后能够用同一工作目录、参数和 Device 选择正常启动；
2. `npu-check` 与应用使用同一套 CANN 环境；
3. 命令只使用 `npu-check --help` 中公开的选项；
4. 日志目标的父目录存在且可写。

仍无法启动时，记录原始命令、工作目录、工具路径、帮助输出、CANN 版本、应用退出码和完整日志。仅使用当前
官方文档明确提供的诊断选项，不根据内部实现猜测修复方法。

## 报告没有源码行号

源码行号依赖算子编译时保留行号信息。先使用报告中的 kernel 名称和 PC 缩小范围，再按项目已有构建方式重新
编译并复测。不要猜测源码位置，也不要提供未经当前项目或官方文档验证的编译参数。

## 超时或卡死

如果测试应用卡在 `aclrtSynchronizeStream` 且允许修改应用，定位期间可临时替换为
`aclrtSynchronizeStreamWithTimeout(stream, 10000)`。`10000` 的单位是毫秒，即 10 秒；返回超时只表示 Host
等待结束，不会终止仍在执行或阻塞的 Device 任务。超时后进入失败清理路径，调用
`aclrtDestroyStreamForce(stream)` 强制销毁仍含未完成任务的 stream，使测试程序快速退出；成功后该句柄失效，
不能继续使用或再次销毁。强制销毁成功前不能释放或复用相关 buffer，也不能将强制销毁视为同步成功。

外部超时可能在报告完成前终止进程。应保留退出状态和原始日志，由 AI 判断超时前的诊断是否有足够上下文作为
局部证据。已有明确诊断且上下文自洽时，报告可判断为部分可靠并保留该问题；没有明确诊断时不能因为暂时没有
错误而声明通过。接口替换、返回值处理和外层保护命令见[运行 npu-check](execution.md)。只有改变明确的卡死
条件或获得新的测试预算后才重试。

## 报告缺失或自相矛盾

AI 应关注以下语义迹象，但不得把它们实现为固定文字或字段列表校验：

- 无法确认报告与哪次命令、环境、输入或检查类型对应；
- 日志缺少关键上下文、明显从中间开始或在分析结束前截断；
- 具体诊断、汇总、应用行为和退出状态之间存在无法解释的冲突；
- 日志显示消息丢失、工具失败或外部终止，可能遗漏后续诊断；
- 报告经过手工拼接、跨版本混用或重新排序。

若已有上下文充分的明确检查诊断，继续向用户报告该问题，并说明整体报告为何只能判断为部分可靠、哪些数量或
覆盖结论仍无法确认。若来源和关键上下文均不能确认，则判断为不可靠，不从中推导算子通过或失败。

只有修复明确原因后才可重试。确定性的基础设施错误发生后，重复执行相同命令不会增加有效证据；应停止重试，
并报告准确的阻塞原因和日志路径。

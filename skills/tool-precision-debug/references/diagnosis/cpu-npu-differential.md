# Reference、CPU 与 NPU 差分

需要借助参考实现、CPU 观察或设备实验缩小精度异常范围时使用。先按当前疑点选择对照路线，再确认结果可以回答什么；已有可信输入输出和运行记录可直接复用。

## 选择对照路线

reference、CPU 孪生与 CPU 算术模型可能都在 CPU 上运行，但用途不同：

| 对照对象 | 主要用途 | 何时使用 |
| --- | --- | --- |
| 项目 reference / golden | 按项目验收标准判断输出是否符合预期 | 确认最终精度结果，或取得语义匹配的阶段参考 |
| CPU 孪生执行 | 在 CPU 调试环境中执行 Kernel，观察控制流、索引、搬运和中间值 | 相关 CPU 路径可运行，且这些观察能区分当前候选 |
| CPU 算术模型 | 模拟局部公式或数值路径，比较候选对同一输入的预测 | 需要区分舍入、结合序、clamp 等解释，模型比反复真机实验更省成本 |
| NPU 实际执行 | 观察目标设备上的失败、关键中间值及修改效果 | 需要确认真实路径或设备相关行为，或者 CPU 路线无法回答当前问题 |

已有可信 golden 和 NPU 失败时，可直接检查源码或采集设备观察。CPU Debug 的成本取决于工程支持、构建和运行准备；无法运行、产品或编程形态不支持时保留缺口，继续选择可行的路线，不把搭建 CPU 环境作为定位前提。具体接口和示例使用 `/ascendc-docs-search`，目标架构能力使用 `/npu-arch`。

## 建立可比条件

参与本次对照的执行应复用同一实际输入和属性。尤其核对目标 dtype 量化后的输入值、shape/axis、layout 映射、有效区，以及两端实际采用的分支；用同一随机种子重新生成数据不自动保证输入相同。必要的运行身份核对见[复现性方法](reproducibility.md)。

**最终验收**：沿用项目 reference 和比较器；需要确定标准或构造 golden 时使用 `/ops-precision-standard`。项目采用高精度 golden 与容差时，高精度参考与逐步低精度实现可以按该标准比较，不要求两者内部舍入过程相同。保留原验收结果，局部模型用于解释差异，不替换验收 golden 来消除失败。

**中间定位**：对齐观察点的公式、输入来源、dtype、量化位置、layout 和有效区，再选择局部参考。搬运看对应元素，Cast 看转换规则，归约看实际参与的输入、累加精度及相关顺序要求。高精度整式的最终结果不能直接充当任一低精度中间张量的期望值。累计偏差参考与基于实际阶段输入的局部重放用途不同，按[观察点设计](checkpoint-design.md#准备局部对照)选择，不混成同一条正常/异常边界。

构建失败、命令未启动或未采到所需输出，属于执行或观察缺口，不记作数值 PASS/FAIL。比较有效时保留实际判定；参考或采集语义不足时按 checkpoint 方法保留 `AMBIGUOUS`，补对照或继续不依赖该观察的分析。

## 解释分叉并选择下一步

下表的 CPU 指 CPU 孪生执行，PASS/FAIL 指它与 NPU 各自在当前输入下按适用项目判据得到的结果。CPU 孪生不自动成为 NPU 的 golden；两端能否直接作数值或位比较，仍取决于该点的比较规则。

| CPU / NPU 结果 | 怎样解释与继续 |
| --- | --- |
| PASS / FAIL | 先核对入口数据、属性与实际路径，再把有区分力的观察点对应到 NPU。入口已不同就向上游检查；入口相同而某阶段输出开始偏离时，查该段实现与依赖 |
| FAIL / FAIL | 比较首个失配位置、错值和触发条件。特征相同时优先查共享公式、索引、参数及参考映射；特征不同时分别缩小范围，不能仅凭两个 FAIL 认定同一原因 |
| FAIL / PASS | 先查 CPU 独有分支、构建配置、模拟实现、输入准备和局部参考。不因 CPU 失败就修改 NPU 路径；本轮 NPU 通过也不抹去尚未解释的原始失败 |
| PASS / PASS | 只说明本轮覆盖范围按标准通过。两端仍可能存在允许的数值差异；原问题尚未复现时回查原输入、产物和触发条件 |
| 任一端无法运行、缺观察或不可比 | 保留具体缺口，补齐必要条件或改用可行路线，不从缺失结果推断正确性或根因 |

例如 CPU 通过，而 NPU 在某个 Cast 后出现差异，应先比较两端 Cast 的实际输入、参数与输出映射。输入已不同就调查 Cast 之前的路径；输入可比时再核对转换规则和实际调用，必要时取得设备观察。不能只因两端结果不同，就认定是硬件舍入问题。

差分用于缩小候选范围，首次分叉不等于根因。依据观察与源码事实按[假设与实验方法](hypothesis-experiment.md)验证具体机制；已有充分证据可复用，不为完成对照流程增加无用实验。

## CPU 与设备检查

需要控制流、offset/count、tile 参数或中间值时，按现有工程的 [CPU Debug 运行与断点说明](../../scripts/usage/asc-tools-probe.md#cpu-debug)执行，并按[观察点设计](checkpoint-design.md)选择相关核、分片和轮次。安装不明或调用失败时再用[能力探测器](../../scripts/usage/asc-tools-probe.md)；探测可用不代表本次 Kernel 已运行。需要自动数值比较时保留相应 dtype 的实际值，终端打印的少量舍入小数不足以代表完整张量或原始位模式。

涉及核间同步时，先保留无断点运行和设备侧观察；单子进程 gdb 示例不适用于这类调试。确需 CPU 断点时按链接中的多子进程说明操作，保留断点对进程调度与原始现象的影响。

CPU Debug/gdb 提供 CPU 域执行与单步观察，npu check 随 CPU 调试检查内存、Tensor 生命周期、队列、同步及部分多核访问问题。日志优先用配套的 `ascendc_npuchk_report.py`，需要结构化整理时再用[日志适配器](../../scripts/usage/npuchk-parser.md)。这些 CPU 域检查可提供定位线索，但不构成 CPU 与 NPU 的设备调度、缓存、并发及数值行为全面等价的保证。产品与编程形态支持按当前配套说明确认。

解释 npu check 报告前核对 CPU Debug 是否正常退出、相关核或轮次是否实际执行，以及本轮日志是否产生。ASSERT 或异常中断后日志可能不完整，应保留“检查未完成”，先调查退出原因或改用其他观察，不能从空报告或无告警排除候选；完整性说明见[日志解释](../../scripts/usage/npuchk-parser.md#输出怎样解释)。

需要调查真实设备执行中的内存、竞争、未初始化或同步异常时，查当前安装的 msSanitizer。能力取决于芯片、CANN 配套版本与编译选项；最新指南中的能力不能直接当作旧安装已经支持。[官方使用指南](https://github.com/Ascend/mssanitizer/blob/master/docs/zh/user_guide/mssanitizer_user_guide.md)、[编译配置](https://github.com/Ascend/mssanitizer/blob/master/docs/zh/user_guide/compile_option_config.md)。按疑点选择检查项，告警需要与源码及原始错值关联，无告警也不能替代数值验收。

CPU 路径自身失败时，先定位其具体表达式、搬运或输入问题，再判断 NPU 是否共享该实现及触发条件。CPU 通过而设备失败时，可把已建立的语义观察点带到 [NPU Dump](dumptensor.md)，核对数据就绪与插桩影响；CPU 的正常边界不直接排除设备侧代码。

## 算术链与设备探针

### CPU 算术模型

结合序、clamp、错误中间量或不同舍入点都能解释 actual，且 CPU 模型能降低区分成本时，模拟相关的局部算术链。按实际竞争解释建立候选即可，不要求每次实现完整的“当前实现、候选修复、oracle”三套模型。

按已确认的中间 dtype、Cast、累加方式与舍入点建模。末尾一次 `astype` 不能代替实际存在的逐步缩窄；也不能机械地在源码每个运算符后加 Cast。例如目标若执行融合乘加，乘法后没有独立舍入步骤，是否发生融合仍需按本次 API、编译或设备证据确认。未知的舍入或求值方式可分别作为候选，NumPy/标准库行为不自动等于设备 API。

先选能区分候选的少量原失败样本和正常对照，保留输入、实际输出、候选预测及采用的比较方式。问题涉及舍入、精确编码或特殊值时再保留必要位模式，NaN/Inf/subnormal 与边界样本按当前疑点及项目输入范围选取，不要求每次覆盖所有类别。缺 golden 时仍可比较候选预测，但这不构成最终验收。

先用源码数据流排除不可能影响失败输出的候选，再选择预测差异最大的输入或观察点。模型与 actual 吻合只提高候选优先级；根据 actual 调整过的模型，要用未参与拟合的数据或独立观察再区分，不能把同一批拟合结果称为独立证明。参考实现也不应复用可能掩盖错误的 helper。

后续实验应检验事先给出的错值、位置或数值类别预测，并控制相关混杂因素。只有观察有效且能区分竞争解释时，才支持相应机制；仅误差下降、按预测方向变化，或多个候选都预测同样结果时，仍需保留未决解释，具体按[实验结果解释](hypothesis-experiment.md#解释结果)处理。

### 最小硬件数值探针

目标版本的文档或源码不能回答关键设备行为、与当前观察冲突，或需要确认实际生成代码时，再考虑 NPU 最小探针。能由当前权威资料或已有可信观察回答的问题，直接复用，不重复搭建探针。

围绕一个待确认行为固定相关 API、模式、dtype 和编译条件，使用触发样本及普通对照；调查表示边界时，再加入边界前后相邻的可表示值。检查数值产生、搬运和消费分别发生在哪里，避免把搬运或解析差异归因于算术。需要解释位级行为时保留输入与输出位模式，并确认缩减后的探针实际走到了目标路径。

记录实际芯片、CANN、编译选项、API 模式、输入范围和观察结果；重复性有疑点时按[复现性方法](reproducibility.md#判断稳定性)处理。结果只覆盖实际执行的组合，不能外推其他架构、版本或模式。探针与被检验实现共享同一近似算法时，二者一致不能当作独立正确性证明。

用探针结果修正候选模型后，回到原始失败输入和实际 Kernel 验证。若与适用的官方资料冲突，保留对应文档、设备环境、调用条件和原始观察，先排查路径与解释差异，不直接改写任一方的结论。

## 改变 dtype 时核对哪些变化

“改成 FP32 就通过”可能同时涉及输入量化、中间算术、编译分派和 tiling 变化。这样的观察可以缩小候选，但不能仅凭最终 PASS/FAIL 将原因归为累加精度。按实际改动核对以下层面，复用已有记录即可：

| 层面 | 核对内容 | 存在变化时怎样继续 |
| --- | --- | --- |
| 数学目标 | 公式、shape/axis、有效元素、常量和 reference 定义 | 先确认仍在比较同一任务，明确同时改变的算法或参数 |
| 输入表示 | Host 原始值、各 dtype 量化后的值与 Kernel 入口值 | 区分输入已经变化和同一输入在计算中产生差异 |
| 实际计算路径 | 模板/重载、API 模式、中间 dtype、已确认的融合与舍入点 | 将实现路径差异列为候选，选择能区分它与输入量化的对照 |
| tiling 与执行范围 | tile/repeat、核数、尾块、对齐和实际参与集 | 核查分片与参与范围；无法单独控制时保留组合解释 |

需要单独调查运算中的 dtype 影响时，可选各 dtype 都能精确表示的公共输入；调查输入量化或表示边界时，则保留各自相关边界点。比较的是入口解码后的数学值，不要求不同 dtype 具有相同位模式。两类样本的用途不同，按本轮问题选择。

若相关条件已受控，首次差异随明确的 Cast 或累加点变化，可提高该数值路径候选；分派和 tiling 同时变化时，保留实验的有效观察，再选择能区分这些解释的输入或局部检查。只在某 dtype 上拟合 NPU 的 CPU 模型也不是设备机制证明。

## 记录结果与收口

记录比较范围、采用的 reference 或模型假设、关键差异、支持的代码候选及尚未区分的原因，沿用已有输入、产物和运行证据。需要自动留存执行时使用[执行器](../../scripts/usage/run-with-evidence.md)，新增模型、采集值与报告保存到[任务产物目录](reporting.md#任务产物目录)，不重复建立台账。

结果应落到实际路径上的代码、数据依赖或仍待确认的局部范围，不能把“CPU 与 NPU 不同”作为根因。只定位任务交付已有证据与限制；修复任务按[主流程阶段 4—5](../../SKILL.md#六阶段调试流程)回放原失败并做相关回归。正式修复有意改变内部 dtype 或 tiling 时说明影响，保留原外部接口与验收要求；调试对照本身不代替修复和验证。
